# V1.5 — Pré-diagnóstico de host e implantação condicionada

**Situação:** o laboratório Docker não foi implantado. A conexão disponível nesta etapa fornece acesso aos workflows n8n e ao GitHub, mas **não** ao Docker Engine, SSH ou Portainer do servidor. Nenhuma conclusão sobre capacidade ou isolamento do host pode ser confirmada remotamente.

## 1. Executar preflight somente leitura

Na máquina Linux que hospeda o Docker:

```bash
git clone --depth 1 --branch feat/public-reference https://github.com/ArnoldReis/laboratorio-testes-n8n.git
cd laboratorio-testes-n8n
bash scripts/preflight-v15.sh
```

Se o repositório já existir, atualize a branch existente antes de executar o script. Nenhum `sudo` é usado; a conta precisa ter acesso de leitura ao Docker para obter métricas.

O script **não executa docker run, compose up/down, restart, exec nem mutações**. Ele observa CPU disponível, `MemAvailable` (inclui cache reutilizável), filesystem do Docker, versão do Compose, quantidade de containers e volumes, consumo pontual de CPU/RAM e se há listener na porta TCP 5688.

A saída pode conter **nomes dos containers** e outras referências operacionais. Revise antes de compartilhá-la fora do ambiente de trabalho e não inclua chaves, `.env`, senhas ou dados de cliente.

## 2. Critérios mínimos para solicitar implantação

- Docker Engine e Compose v2 funcionais, sem conflitos de serviço.
- Memória efetivamente disponível compatível com o teto previsto de 1536 MiB no n8n e 128 MiB no mock, mais overhead do host e processos auxiliares. Alerta abaixo de 3072 MiB livres em `MemAvailable`.
- Pelo menos 6 GiB livres no filesystem do Docker, antes de baixar imagens e criar volumes (limiar de triagem, **não** garantia de espaço).
- Porta 5688 sem listener no host; caso esteja ocupada, escolher outra porta local antes da implantação.
- Revisão do desempenho dos serviços já existentes: picos de CPU e pressão de RAM do modelo de IA local são motivo para **não** iniciar novos serviços até agendar uma janela de testes.
- Sem volumes, segredos, credenciais ou redes de produção compartilhados.
- Conexão externa bloqueada por testes efetivos de rede, nunca apenas pela presença de `internal: true` no YAML.
- Aprovação humana da configuração, do plano de rollback e do consumo de recursos.

Esses limiares são **triagem conservadora**, não um dimensionamento definitivo do host. CPU do lab limitável por cgroup ainda compete com os serviços reais.

## 3. Verificador posterior à implantação (ainda não executado no host)

Quando a equipe aprovar o provisionamento da stack e os dois containers **já estiverem em execução**, utilize o verificador manual:

```bash
bash scripts/verify-lab-v15.sh
```

O script é de **leitura e validação**, não instala a stack e não reinicia containers. Ele verifica:

- Compose de laboratório válido e os dois containers existentes, em execução e sem modo privilegiado;
- cada container conectado exclusivamente à mesma rede Docker interna, com exatamente dois membros;
- editor n8n publicado exclusivamente no loopback TCP `127.0.0.1:5688`, sem publicação da porta do mock;
- volume exclusivo do n8n do laboratório e ausência de mounts críticos conhecidos;
- chamadas sintéticas ao mock retornando HTTP 200 e HTTP 503 sem entregas externas;
- tentativa HTTPS para `example.com` **bloqueada**, com timeout curto.

Uma verificação que falhar produz `BLOQUEADO`. Mesmo quando todas passam, **o resultado não autoriza workflows de produção**: a revisão humana de firewall, isolamento de volumes, configuração de credenciais, CPU e logs continua obrigatória.

> O verificador usa `docker compose exec` para executar **somente JavaScript de teste dentro do container n8n do laboratório**. Nenhum node de produção é invocado. Não envie `.env.lab` nem a saída completa do `docker inspect` para serviços externos.

## 5. Etapas seguintes, depois de receber as métricas

1. Revisar o diagnóstico com o operador e ajustar limites sem causar contenção.
2. Gerar chave **nova** para n8n do laboratório, definir imagem com versão/digest validado e executar `docker compose config --quiet`.
3. Revisar isolamento de rede e montagens, então fazer a implantação explícita na stack isolada.
4. Testar health e respostas mockadas; confirmar falha de acesso a Internet e redes de produção.
5. Documentar evidências sanitizadas e obter autorização antes de homologar um workflow real.

**Regra:** não alterar n8n, Postgres, Redis, Ollama nem containers corporativos para instalar o laboratório. O próximo avanço só acontece com diagnóstico do host e revisão do isolamento.
